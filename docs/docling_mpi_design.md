# 基于 Docling 的多节点智能分片并行处理系统设计

## 1. 设计目标
- **处理对象**：PDF 中的表格、文本、图像等多模态信息。
- **性能目标**：利用 MPI 搭建多节点集群，实现高吞吐低延迟的并行处理。
- **扩展性目标**：支持节点横向扩展、任务弹性调度、可插拔的模型与解析插件。
- **鲁棒性目标**：面对节点波动时具备自动重试和回收机制，确保任务完整。

## 2. 总体架构
系统采用分层架构：

1. **协调层（Coordinator）**：在 MPI 中以 `rank 0` 运行，负责任务分片、调度、全局状态维护、故障监控。
2. **工作层（Workers）**：其余 `rank` 节点，负责分片处理 PDF 内容并上传结果。
3. **存储与消息层**：外部持久化（对象存储/共享文件系统）与元数据存储（Redis/PostgreSQL），用于存放原始文档、分片描述、处理状态。
4. **模型服务层**：封装 Docling 解析流程及可选的 OCR/LLM 推理服务，通过 gRPC/HTTP 服务供 Worker 调用。

MPI 提供节点间控制流通信；数据流通过共享存储或对象存储传递，避免大文件在 MPI 内部传输。

```
+-----------------------+           +-----------------------+
|       Coordinator     |<--------->|   Metadata Store      |
|  (MPI rank 0)         |           |  (Redis/PostgreSQL)   |
+-----------+-----------+           +-----------+-----------+
            |                                   |
            | MPI 分发控制信息                   |
            v                                   v
+-----------------------+          +------------------------+
|       Worker i        | <------> |   Object Storage /     |
|  (MPI rank i, i>0)    |          |   Shared File System   |
+-----------+-----------+          +-----------+------------+
            |
            | 通过 gRPC/HTTP 调用 Docling & OCR 服务
            v
+-----------------------+
|   Docling Service     |
+-----------------------+
```

## 3. 智能分片策略
1. **文档结构分析**：Coordinator 使用 Docling 的布局分析模块对 PDF 做轻量预解析，获取页面、逻辑块、表格边界等信息。
2. **多维度分片**：
   - **按页面分片**：基础单位，确保任务均匀；
   - **按内容类型**：表格、文本、图像分别标注，用于调度时匹配具备相应模型/资源的 Worker；
   - **按复杂度评分**：根据表格密度、文字量、图像大小给出复杂度权重，指导负载均衡。
3. **分片描述符**：包含 `doc_id`、`page_range`、`content_types`、`complexity_score`、`dependencies` 等字段，存入元数据存储。
4. **动态调整**：Coordinator 监控 Worker 的吞吐和队列长度，必要时重新分片或迁移未开始任务。

## 4. 处理流水线
### 4.1 Coordinator 流程
1. 接收待处理 PDF（从消息队列或上传 API）。
2. 触发 Docling 轻量解析，生成结构化布局。
3. 生成分片列表并写入存储，同时通过 MPI 广播任务元数据。
4. 维护任务队列：使用 MPI `MPI_Send`/`MPI_Recv` 或 `MPI_Scatterv` 逐个/批量分发分片描述。
5. 聚合结果：通过 MPI `MPI_Gather` 或异步消息接收 Worker 的处理完成信号，并更新元数据存储。
6. 处理失败任务：重试、降级或标记人工处理。

### 4.2 Worker 流程
1. 启动后向 Coordinator 发送 `READY` 消息并声明处理能力（如 OCR/GPU 支持）。
2. 接收分片描述，下载对应页面或局部内容。
3. 根据内容类型调用 Docling 服务模块：
   - **表格**：Docling 表格解析 + 表格结构修复；必要时调用结构化重建模型。
   - **文本**：Docling 文本提取 + NLP 后处理（语言检测、摘要、实体抽取）。
   - **图像**：Docling 图像导出 + OCR/视觉模型处理（如版面矫正、Caption 生成）。
4. 将处理结果写回对象存储，并向 Coordinator 发送完成消息（包含结果位置、统计指标）。
5. 处理失败时回传错误类型，Coordinator 根据策略决定重试或转人工。

### 4.3 Docling 服务封装
- 为降低 Worker 压力，Docling 模块部署为可扩展的服务（容器化，支持 GPU）。
- 提供统一接口：`ParseTable`, `ParseText`, `ParseImage`，支持批处理。
- 采用异步队列与连接池管理，保证高并发。

## 5. MPI 通信设计
- **初始化**：所有节点通过 `MPI_Init` 启动，Coordinator 在 `rank 0`。
- **能力注册**：Workers 使用 `MPI_Send` 将能力描述发送至 Coordinator；Coordinator 使用 `MPI_Bcast` 广播全局配置。
- **任务分发**：
  - 采用非阻塞通信（`MPI_Isend`/`MPI_Irecv`）提高吞吐。
  - 支持任务拉取模式：Worker 通过 `REQUEST_TASK` 消息申请，Coordinator 回复分片。
- **结果收集**：Worker 完成后发送 `RESULT_READY` 消息，包含状态码及结果元数据。
- **心跳与监控**：周期性发送 `HEARTBEAT` 消息，Coordinator 超时未收到则标记节点故障。
- **故障恢复**：未完成任务重新入队；可选择启用备用节点或动态扩容。

## 6. 资源与调度
- **Worker 角色划分**：
  - `TableWorker`：拥有强 CPU/内存，专注复杂表格解析。
  - `TextWorker`：CPU 型，负责大规模文本提取与 NLP。
  - `ImageWorker`：GPU 型，执行 OCR/图像增强。
- **调度策略**：基于能力标签与当前负载，Coordinator 将合适的分片分配给对应 Worker。
- **弹性扩展**：结合容器编排（Kubernetes + MPI Operator），实现节点动态加入与退出。

## 7. 数据存储与结果聚合
- **原始 PDF**：存储于对象存储（S3、OSS）或共享文件系统。
- **中间结果**：按分片存储 JSON/Parquet，命名含 `doc_id` 和 `shard_id`。
- **最终结果聚合**：Coordinator 汇总各分片结果，按页面顺序或内容类型合并，生成统一输出（如 JSON、数据库记录、知识图谱条目）。
- **版本管理**：为每次处理生成任务版本号，支持回滚与审计。

## 8. 监控与可观测性
- 使用 Prometheus/Grafana 监控节点状态、任务成功率、处理时延。
- 日志采集（Fluentd/ELK）记录关键事件、错误堆栈。
- 通过消息队列或 Webhook 通知处理完成。

## 9. 安全与权限
- 对存储和服务访问启用基于 IAM/Token 的访问控制。
- 敏感 PDF 可采用加密存储与传输（TLS/HTTPS、KMS）。
- Worker 节点运行在隔离容器，限制权限和资源使用。

## 10. 开发与测试建议
- 使用单元测试验证 Docling 服务接口输出。
- 构建集成测试：模拟小规模 MPI 集群，验证分片调度、负载均衡、失败重试。
- 压力测试：使用真实 PDF 数据集评估吞吐量与延迟。

## 11. 未来扩展方向
- 引入任务优先级、基于强化学习的调度策略。
- 集成 LLM 对复杂表格进行语义理解，生成结构化知识。
- 支持多格式文档（Word、HTML）统一处理。
